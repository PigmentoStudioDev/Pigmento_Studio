## La verificacion en vivo, pegada

Servidor de produccion (`pnpm start`) contra la base local, con una propuesta
sembrada por la Local API (`status: enviada`, `notes:
NOTA-INTERNA-QUE-NO-DEBE-SALIR`, dos renglones de 1050 y 2075 centavos).

```
$ curl -o /dev/null -w 'HTTP %{http_code}' localhost:3000/propuesta/12e1f8a9-…
HTTP 200
$ curl -o /dev/null -w 'HTTP %{http_code}' localhost:3000/propuesta/00000000-0000-0000-0000-000000000000
HTTP 404
$ curl -o /dev/null -w 'HTTP %{http_code}' localhost:3000/propuesta      # sin token
HTTP 404
$ curl -w '\nHTTP %{http_code}' localhost:3000/api/proposals
{"errors":[{"message":"You are not allowed to perform this action."}]}
HTTP 403
$ curl -w '\nHTTP %{http_code}' 'localhost:3000/api/proposals?where[accessToken][equals]=12e1f8a9-…'
{"errors":[{"message":"You are not allowed to perform this action."}]}
HTTP 403
```

La quinta es la que importa: **conocer el token no abre el REST**. El endpoint no
distingue "sin sesion con token bueno" de "sin sesion a secas", asi que la unica
puerta por la que sale una propuesta es la pagina, que mapea campo a campo.

Sobre el HTML de la propuesta buena:

| Cadena buscada | Veces |
| --- | --- |
| `NOTA-INTERNA-QUE-NO-DEBE-SALIR` | 0 |
| `accessToken` | 0 |
| el token | 1 — el arbol de segmentos del router, o sea la URL que el cliente ya tiene |
| `<meta name="robots" content="noindex, nofollow">` | 1 |
| `$10.50` / `$20.75` / `$31.25` | los tres |

La ruta sale como `ƒ (Dynamic)` en la tabla del build: se renderiza a peticion y no
hay ninguna cotizacion escrita en `.next/`.

## Lo que encontro `security-reviewer`, y como quedo

Ningun CRITICAL ni HIGH. Dos MEDIUM, los dos reales, los dos arreglados con test en
rojo primero.

**1. `admin.readOnly` no protege el `accessToken`.** Es una propiedad del PANEL —vive
bajo el tipo `AdminClient`, no bajo `access` del campo— y el hook era
`({ value }) => value || randomUUID()`, que conserva cualquier valor truthy. Con
`access.update` de la coleccion en `Boolean(user)`, **cualquiera con sesion podia
mandar `PATCH /api/proposals/1 { "accessToken": "pigmento2026" }`** y a partir de ahi
la cotizacion de ese cliente la abre quien adivine la palabra.

Arreglado en dos capas, porque una sola no cubre las dos puertas:

- `access: { create: () => false, update: () => false }` en el campo. La doc del tag
  v3.88.0 lo dice literal: *"If false is returned, any passed values will be
  discarded"*. Cubre REST, GraphQL y el panel — todo lo que respeta el control de
  acceso. **No cubre la Local API**, que lo salta por defecto.
- `mintAccessToken`, que **ignora el valor entrante**: al crear acuna uno nuevo, al
  actualizar devuelve el guardado. Es la que cierra las dos puertas, y esta exportada
  por su test como `toPiece` en S4.

Verificado contra el servidor de produccion con una sesion real:

```
create con {"accessToken":"pigmento2026"}  → 4d911797-1388-4134-913e-2e469fc44671
PATCH  con {"accessToken":"pigmento2026"}  → token sin tocar
/propuesta/pigmento2026                    → 404
/propuesta/<el real>                       → 200
```
Y la Local API, que salta el control de acceso del campo, tambien devuelve UUID: eso
es lo que demuestra que quien cierra la puerta es el hook y no el `access`.

**Aviso de metodo, que costo una vuelta entera:** la primera tanda de estas medidas
dio "el REST guarda el token forjado" y estuve a punto de reportarlo como fallo del
fix. Era falso. `pkill` no habia matado el servidor anterior, el `pnpm start` nuevo
murio con EADDRINUSE en un log que no mire, y **curl estaba hablando con el build de
antes del arreglo**. Se ve en `ps -o lstart`. Comprobar el reloj del proceso antes de
creerse una medida.

**2. El gate de la consulta se dejaba enganar por un comentario.** La regla exigia que
las cadenas `accessToken` y `limit: 1` aparecieran EN ALGUN SITIO del argumento de
`payload.find`. Asi que esto pasaba verde:

```ts
payload.find({ collection: 'proposals', where: { id: { equals: x } }, limit: 1, /* accessToken */ })
```

…devolviendo cotizaciones por un id numerico adivinable. Era el unico backstop
automatico de la propiedad que sostiene toda la seguridad de esta coleccion. Ahora el
runner **quita los comentarios** y `accessToken` se exige **como campo del `where`**,
que se aisla equilibrando llaves. Los cuatro rojos estan en la tabla de arriba, la
trampa exacta incluida.

**Los tres LOW.**

- *Entropia de `crypto.randomUUID()`*: suficiente. ~122 bits de CSPRNG, sin secuencia
  ni marca de tiempo en el formato. Sin cambios.
- *Cacheado*: hoy ya era seguro —la ruta sale `ƒ Dynamic` y responde con
  `Cache-Control: private, no-cache, no-store`— pero por accidente. Se declara
  `export const dynamic = 'force-dynamic'` **y lo vigila un gate**, para que quitarlo
  sea un diff y no un descuido. El escenario que cubre es real: envolver la consulta
  en `unstable_cache` "para que vaya mas rapido".
- *Validacion en la frontera*: `getProposalByToken` comprueba ahora el TIPO y no solo
  la verdad. Hoy `[token]` siempre da un string —seria `[...token]` quien diera un
  array— pero la funcion esta exportada y no puede depender de que quien la llame sea
  de fiar.
- *Oraculo de tiempo* entre 404-por-token-malo y 404-por-borrador: medido, 15
  peticiones de cada, ~1.0-1.3ms con solapamiento total. No hay canal lateral, y
  daria igual: el espacio de tokens no se recorre a fuerza bruta.

## Decisiones

1. **`getProposalByToken` NO lleva `overrideAccess: false`, y va contra lo que decia
   el spec.** El spec lo daba por obvio; al implementarlo resulta que es lo contrario.
   Con `access.read` exigiendo sesion —que es lo que cierra el REST— un visitante
   anonimo con `overrideAccess: false` no leeria **ni su propia propuesta**. La salida
   tentadora, abrir `read` a anonimos, es peor: abre TAMBIEN el REST y entonces
   cualquiera lista todas las cotizaciones sin token. Payload no puede condicionar el
   acceso a la consulta porque el control de acceso no la ve.

   Asi que la seguridad de esa lectura descansa en tres cosas, y las tres las vigila
   el gate `lecturas` con una regla `porColeccion` propia para `proposals`:
   el `where` filtra siempre por `accessToken`, `limit: 1` impide enumerar, y `toView`
   mapea campo a campo. **`overrideAccess: false` sigue siendo obligatorio para todo
   lo demas** (`porDefecto`), que es como esta `projects`.

2. **El borrador tampoco sale.** La ruta llama a `notFound()` si el status es
   `borrador`: una cotizacion a medio pensar tiene precios que aun no son una oferta.
   Misma respuesta que un token inventado, para no volver la URL un oraculo.

3. **El total se calcula al leer, nunca se guarda.** Un total almacenado puede acabar
   contradiciendo a sus renglones —basta con editar uno y que falle el hook— y
   entonces la cotizacion dice dos cosas a la vez.

4. **El organismo recibe `locale` como prop.** `Intl.NumberFormat` necesita un idioma
   y el idioma es cosa de la pagina; con el literal dentro, el design system tenia
   escrito `es-MX` y dejaba de poder salir del repo.

5. **`notification-background-warning` se pide por `_component-tokens.scss`.** El
   aviso de vencida uso primero `theme.$notification-warning-background`, que no
   existe: los `notification-*` son tokens de COMPONENTE (tercera capa) y no viven en
   `theme`. El puente valida el nombre contra los mapas de Carbon en compilacion, asi
   que el error salio como error y no como custom property huerfana.

## Deuda que deja abierta

- **En la base local quedan una propuesta de prueba (id 1) y un usuario de revision**
  (`revision-s5@example.invalid`). `pigmento.db` esta en `.gitignore`; borrarlos desde
  el admin cuando estorben.
- **La columna `access_token` es NULLABLE.** El indice UNIQUE de SQLite admite varios
  NULL, asi que el invariante "toda propuesta tiene token unico" lo sostiene el hook y
  no el esquema. Ponerlo `NOT NULL` no es `required: true` en el campo —la validacion
  corre ANTES del `beforeChange` que lo acuna, asi que rechazaria todo create— sino
  una migracion escrita a mano. Se deja anotado en vez de hacerlo a medias.
- **Sin adaptador de email**: Payload avisa en cada arranque y el reset de password
  escribe a consola. Es de S7.
- **Los deploys de preview migran contra la base de produccion de Turso.** Sigue sin
  resolverse y ahora hay datos de clientes detras. Es lo primero de S7.
